### Manual QA plan (Odoo)

Odoo supplement to `nalgene-mode`'s `playbooks/manual-qa-plan.md` — read that file first for the shape (setup vs. cases, Pass/Fail, naming what's hidden); this file is only the Odoo-specific conventions for filling it in. The medium (step 2 of the generic playbook) is almost always the Odoo web client itself.

1. **Source material**, richest first, same priority order as the generic playbook: a Gherkin-style audit already cross-checked against the module's OpenSpec capability (some modules keep one as its own doc, e.g. a `docs/TEST_COVERAGE_AUDIT.md` alongside this plan) beats `playbooks/coverage-audit.md`'s own gap table (which doesn't reference OpenSpec), which beats reading the module cold against its OpenSpec capability directly.
2. **Name every screen by what's actually on it**, not the technical name: the menu path as a user clicks it (**Inventory app → Operations → Transfers**, not `stock.picking` list view), the exact button label, the exact field label — not the `_name`/technical field name. Pull labels from the view XML's `string=`, not the Python field definition, since that's what actually renders.
3. **One-time setup, Odoo-specific items to check for**: Developer Mode (**Settings → General Settings**, bottom of page, **Activate the developer mode** — needed for anything under **Settings → Technical**), a test user with the right security group(s) (**Settings → Users & Companies → Users**, the module's own group row), any `ir.config_parameter` the feature reads (**Settings → Technical → System Parameters**, with the exact key and what value unblocks or speeds up testing), and any seed/demo data the cases assume already exists.
4. **Name what the UI deliberately hides, Odoo's own common shapes**: a hashed/encrypted field with no plaintext anywhere in the UI, a field restricted to one security group so most testers can't see it at all, a computed field with no form-view widget. For each, give the actual indirect check available in this project — the chatter log (`message_post` notes), the record's status bar / state widget, a different screen that does show a related value, or (last resort, call it out as developer-only) Developer Mode's "View Metadata"/record debug menu.
5. **A case that needs a background job or scheduled action** names the exact one (**Settings → Technical → Automation → Scheduled Actions**) and whether the tester runs it manually (the action's own "Run Manually" button) or must wait for its real interval — don't leave "trigger the cron" unstated.
6. **Cross-reference**: put a one-line pointer at the top of each document to its counterpart — the audit names the plan ("for a click-through version, see ..."), the plan names the audit ("for the developer-facing cross-check this was derived from, see ...") — so an edit to one is a prompt to check the other, not a silent drift.
7. **Report**: same as the generic playbook, plus which security group(s) the test user needed and whether any System Parameter had to change from its default to make testing practical.

## Why

Odoo's own view layer already separates "what's stored" from "what's shown" — a field can exist, be fully functional, and never appear on any form the tester has access to. A QA plan that doesn't call this out by name reads as broken ("I can't find X anywhere") instead of as the deliberate access/display design it actually is; naming it up front turns a confusing dead end into a confirmed, intentional result.
