### Integration testing (tours & HttpCase)

Flow for writing and running full browser click-through tests that prove the web client and the server work together, per Odoo's [integration testing reference](https://www.odoo.com/documentation/20.0/developer/reference/backend/testing.html#integration-testing).

1. Create the tour under the module's `static/tests/tours/<name>.js`, with a paired Python test under `tests/test_<name>.py` (imported from `tests/__init__.py`, same as any other test module).
2. Register the tour: `registry.category("web_tour.tours").add("tour_name", { url: "...", steps: () => [...] })`. Each step is an object with `trigger` (a selector the engine polls for until it exists) and optionally `run` (`"click"`, `"edit <text>"`, `"press Enter"`, a named helper, or an async function) and `content` (the tooltip shown when played manually, also logged — write one even on automated-only steps, it's what you read in a failure log). A step with `trigger` and no `run` is a pure wait/assertion: the tour only advances once that element exists, so it doubles as "assert this is visible."
3. Wire the file into `__manifest__.py`'s `'assets': {'web.assets_tests': ['<module>/static/tests/tours/<name>.js']}` — this bundle is separate from `web.assets_unit_tests` (`playbooks/js-testing.md`), which explicitly excludes `tests/tours/**/*`. A tour never runs in the browser without this entry, even when the Python side already calls it by the right name.
4. Drive it from Python: an `HttpCase` subclass calling `self.start_tour(url_path, "tour_name", login="admin")`. The `"tour_name"` string here must be byte-for-byte the same as the registry name in step 2 — a mismatch fails silently as "tour not found" rather than a clear error, so grep both sides for the literal string before running anything. `start_tour` blocks until a real headless Chrome session finishes the tour (success, failure, or timeout) before returning control to Python.
5. Assert rendered UI state (is a button visible, is a value displayed) through the tour's own `trigger` selectors, not Python — a step that never matches times out and fails the test, which *is* the assertion. Assert persisted/business state (field values, computed totals, related records) with plain `assertEqual`/`assertTrue` in Python after `start_tour` returns — the transaction already reflects whatever the tour did.
6. End every tour on a clean, saved state. Per Odoo's own docs, "the last step(s) of a tour should always return the client to a 'stable' state (e.g. no ongoing editions)" — a tour left on a dirty/unsaved form fails even when every step before it matched, because an open edit risks a stray autosave network request racing the test's teardown. Close with an explicit save (`.o_form_button_save`) or a navigation away, then a step that waits for the saved/stable state before the tour ends.
7. Debug a failing or flaky tour with `watch=True` (opens a real Chrome window to watch the run) or `debug=True` (fullscreen Chrome, devtools open, breakpoint at tour start) passed to `start_tour`/`browser_js` — don't debug tour timing blind from server logs alone. On CI/headless failures, `--screenshots`/`--screencasts` capture the failure moment under `/tmp/odoo_tests/{db_name}/screenshots/`.
8. Verify per **principle-prove-it-works**, scoped the same way as `playbooks/backend-testing.md`: `--test-tags module_name:ClassName.method_name` while iterating, not the whole suite — tours are slow, so keep the loop tight.
9. Report: the tour name and URL it runs against, the `--test-tags` value used, and the pass/fail count.
