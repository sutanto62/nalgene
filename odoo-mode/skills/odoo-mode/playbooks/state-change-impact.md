### State-change impact

Fires ahead of `openspec-gate` whenever a request would insert, rename, or alter a model's lifecycle state (`state`, `stage_id`, or any field playing that role). A state value is rarely read in one place — it gets hardcoded as tuples, membership checks, view visibility, and labels in modules that never touch the field's own definition. Map that blast radius before a proposal exists, so the proposal's scope is right the first time.

1. **Check canonical model's state behavior.** Resolve `{CE_PATH}`/`{EE_PATH}` the same way `principle-odoo-reuse-extend` and the `how` skill's Odoo track do. Find the field's own declaration in CE (then EE, if the model plausibly has an EE variant): `fields.Selection([...])`, its default, `tracking`, `group_expand`. Then search CE/EE for the field name **and** every one of its current literal values as plain strings — not just where the field is declared. A value embeds far from the field definition: `in ('done', 'cancel')` terminal-state tuples, `@api.constrains` guards, domains on actions/views (`[('state', '=', 'done')]`), view `states=`/`attrs` visibility and `statusbar_visible`, crons that scan by state, QWeb reports and search-view groupby, record rules scoped by state. Record the current transition graph as found — which value can move to which, and under what guard — before proposing anything; this is the "before" state machine, and it's what step 4's chart renders against. Mistake to avoid: searching only for the field name — a grep for `state` finds the declaration and obvious `self.state ==` checks, but misses a tuple like `('delivered', 'done')` that never names the field nearby (it's a module-level constant checked against several fields, or copied into a sibling model).
2. **Check custom model's state behavior.** Enumerate every custom module that `_inherit`s the same model — not just the module the user named. Grep the whole custom tree for `_inherit = "<model>"`. For each one, and for any module that merely reads the field without inheriting the model (a related field, an RPC/portal read, a webhook payload builder, an intercompany sync), search for the field name and every literal current value — the same two-pass search as step 1. Watch for these shapes specifically, because they're exactly where this kind of change tends to break: a terminal-state tuple duplicated in more than one module; a `previous_state` string captured once and never re-derived from the actual prior state; a status/label map feeding an outbound integration (webhook, API, portal); a count/summary breakdown keyed by state; view statusbar or decoration lists. Separate, for each hit, whether it must change (an exact-match check that would now wrongly exclude/include the new or renamed value) from one that's deliberately exact and must stay untouched (a distinct, earlier event in the same lifecycle that the new state doesn't relabel — e.g. an OTP/handoff confirmation step that happens before the new state and isn't the same event as it). Mark the deliberate ones explicitly in the report — don't let them read as an oversight, and don't "fix" them into including the new state. Mistake to avoid: treating this as "check the module the user is editing" — the field's value set gets checked by consumers two or three dependency hops away (an intercompany sync, a transporter API, a webhook log-label map) that never show up from reading the one module in scope.
3. **Analyze impact before writing any report.** Fold steps 1-2 into one list, each entry tagged: **breaks** (an exact-match check now wrong), **extend** (needs the new/renamed value added to its set), or **unaffected-by-design** (deliberately exact — state the reason). Treat a technical-key rename and a label-only rename as different blast radii: a key rename breaks every hardcoded string match found in steps 1-2; a label-only rename breaks none of those, only a selection widget's display text, translations, or any place comparing `display_name` instead of the key — search for those separately, they weren't found by the value-string search above. Check the new/changed dependency edges this impact creates against `principle-odoo-reuse-extend`'s dependency boundary — fixing one module's hardcoded check must not introduce a custom-to-custom `depends`.
4. **Report using one-liner format, with the statechart flow.** One line per finding: `<model>.<field> in <module>: <what breaks> — <why>`. Group by breaks / extend / unaffected-by-design. Draw the current and proposed state machine with `nalgene-mode`'s **statechart** skill: states are the lifecycle's values (as recorded in step 1), actions are the transition methods/buttons found in steps 1-2, and the invariant is whatever the request would otherwise violate (e.g. "a `done` picking is terminal" or "`received` only follows `delivered`"). Read that skill's `SKILL.md` off disk and follow it — same cross-plugin convention `odoo-mode` already uses for every other `nalgene-mode` reference, not a `Skill`-tool dispatch. Hand off both: the one-liner list and the chart's Mermaid text (plus an SVG if the chart is large, per that skill's own render step).
5. **Ask for confirmation. Do not continue to openspec before consent.** Stop after the report. Only proceed into `openspec-gate` once the user has explicitly confirmed scope and direction — silence, or a reply about something else, isn't consent. If the user's confirmation changes scope (e.g. drops one of the "extend" modules), update the impact list before handing it to openspec — don't let openspec start from the pre-confirmation scope.
6. Report: the blast-radius list (breaks / extend / unaffected-by-design), the statechart handed off, and whether the user confirmed before openspec started.
