# Node.js Backend Feature Reference

Build order for a new capability or behavior change in a Node.js/TypeScript backend service (HTTP API and/or event consumer — Express, Fastify, NestJS, Koa, or similar). Each step assumes the ones above it are settled. This is a default layering, not a mandated folder structure: the anti-patterns called out per step matter more than the exact names.

1. **Contract first** — apply **principle-backend-api-contract**: write or update the OpenAPI spec for a new/changed HTTP operation (or a schema-first tool the project already uses — e.g. Zod/`zod-to-openapi`, tRPC, ts-rest), or the AsyncAPI spec (or project equivalent) for a new/changed event, before writing a route handler or publisher. Generate or derive server types from it rather than hand-writing a parallel interface.
2. **Compatibility check** — apply **principle-backend-compat** whenever this touches an *existing* endpoint, event schema, or table: additive by default, expand/contract for migrations, a stated deprecation path for anything narrower.
3. **Layering check** — apply **principle-backend-layering**: detect whether this project already separates route/service/repository. If it does, steps 4-6 below follow that split and anything violating it (business logic in a route handler, a repository making a business decision) is a finding. If it doesn't yet (a new or small service), say so and skip straight to step 4 without scaffolding layers it hasn't grown into needing.
4. **Route/controller layer** — parse and validate the request against the generated/derived type, call one or more service functions or classes, map the result to a response.
5. **Service layer** — business rules, validation beyond request-shape, authorization decisions, and orchestration across repositories/external clients. Depends on its collaborators through constructor injection or a passed-in interface/object, not a directly imported singleton — a module that reaches for a shared client/connection by importing it is what makes step 11 (TDD) hard, not a shortcut.
6. **Repository/data-access layer** — data access only: queries, transactions, mapping rows/documents to domain objects.
7. **External integrations** — a third-party call goes through its own module behind an interface, never called directly from the service or route handler.
8. **Concurrency & performance** — apply **principle-backend-performance**: don't run a synchronous CPU-heavy loop or sync `fs`/`crypto` call on a hot path — it blocks the event loop for every other in-flight request. Offload to a worker thread or a queue; bound any concurrent work (a `Promise.all` over unbounded input is the anti-pattern to flag) instead of firing it unbounded.
9. **Migrations** — forward and backward migration files via the project's migration tool (Knex, Prisma, `node-pg-migrate`, or similar), additive before destructive — see **principle-backend-compat**'s expand/contract pattern.
10. **Security** — apply **principle-backend-security** at the boundary this step introduced: input validation beyond the generated/derived type's shape check, the specific authz decision, parameterized queries (never string-built SQL, regardless of ORM), secrets through the project's mechanism (not `process.env` read ad hoc without the project's config layer), a dependency check (`npm audit`/`osv-scanner`) if a new package was added.
11. **Tests** — TDD per **backend-testing**: the failing test first, dependencies behind interfaces/DI so a unit test can mock them, a separate integration test for the repository/external call.
12. **Report** — what was built, which spec(s) changed, how compatibility/layering/security/performance were addressed or found not to apply, and the test scope/result.

"Node.js backend project" means `package.json` names a server framework (`express`, `fastify`, `@nestjs/core`, `koa`, `hapi`) or the repo exposes server-side routes/controllers, with **no** SPA framework (`react`, `vue`, `@angular/core`, `svelte`) in the same `package.json` — `package.json` alone isn't enough signal, since it also matches `web-mode`'s frontend detection. In a monorepo with both a Node backend and a frontend app, detect per sub-project touched, not per repo.
